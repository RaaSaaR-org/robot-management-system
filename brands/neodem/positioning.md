# NeoDEM — Positioning

## Positioning statement

For robotics manufacturers and teams building Physical AI, NeoDEM is an open, modular platform that connects data collection, model workflows, and fleet operations. It provides shared context across those workflows while letting teams choose compatible hardware, models, and infrastructure.

## Audiences and needs

| Audience | Need | Message emphasis |
|---|---|---|
| Robot manufacturers | Connect their robot to useful software workflows | Embodiment integration, operator experience, supported capabilities, and validation |
| Robotics and AI engineers | Move between demonstrations, datasets, models, and evaluation | Open formats, reproducible configurations, traceability, and extensible interfaces |
| CTOs and technical leads | Coordinate an evolving robotics stack | Modular architecture, deployment control, and explicit integration boundaries |
| Fleet and operations teams | Understand robot state and manage work | Clear telemetry, practical controls, intervention, and operational records |

## Value pillars

| Pillar | Customer value | Evidence to show |
|---|---|---|
| Connected workflows | Keep data, model versions, evaluations, and operations in context | A demonstrated workflow with its prerequisites and readiness |
| Open ecosystem | Retain options for infrastructure, datasets, and compatible models | Open data formats, documented interfaces, and deployment architecture |
| Multiple embodiments | Reuse platform workflows across integrated robot configurations | The supported capability matrix for each robot |
| Visible evidence | Understand what happened and how confidently it is known | Provenance labels, telemetry, evaluation results, and audit records |
| Human control | Make intervention and control ownership explicit | Operator controls and demonstrated stop/recovery behavior |

## Manufacturer integration offer

Integrate a manufacturer's robot as a supported NeoDEM embodiment, with an agreed configuration, hardware connection, telemetry, controls, visualization, and acceptance evidence. Add advanced teleoperation, data collection, learned skills, or autonomous workflows according to the project scope.

Use the [new embodiment integration plan](../../docs/new-embodiment-integration-plan.md) to define deliverables. Separate support for a new robot model from onboarding additional units of a supported configuration.

## Claims discipline

Describe hardware independence as an architectural direction, with integration readiness stated per robot. Describe model choice in terms of compatible interfaces and tested configurations. Support statements about task performance with a named task, setup, and result.

For record-keeping features, describe the records and workflows provided. Avoid blanket certification or guaranteed-compliance claims. Use the [platform documentation](../../docs/platform.md) to check the scope of each feature before publication.
